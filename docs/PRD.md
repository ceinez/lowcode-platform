## 1. 背景与问题（为什么做）

### 1.1 业务现状

电商业务中，"营销活动页"是一个**高频、短周期、强变化**的内容类型：

- **高频**：大促、节日、新品、会员日……一个月可能上几十个活动页
- **短周期**：单个活动页生命周期往往只有几天到两周
- **强变化**：活动规则、优惠力度、商品池频繁调整，页面要跟着改

### 1.2 核心痛点：生产模式错配

当前一张活动页的生产链路是：

```
运营提需求 → 前端排期 → 开发 → 联调 → 上线
```

一张结构简单、复用度高的活动页，平均要 **3 人天**。

但它的内容本质是"轮播、商品、优惠券、公告这些**固定组件的排列组合**"——这是一种**低创造性的、可标准化的研发工作**。

### 1.3 一句话总结

> 页面是"标准化组件 + 个性化配置"的产物，但生产方式是"手工作坊式定制开发"，产能瓶颈卡在了前端。

---

## 2. 产品目标（达成什么目的）

**北极星指标：让运营不依赖前端，自己完成活动页的搭建、预览、发布。**

| 目标 | 指标         | 现状        | 目标值                 |
| ---- | ------------ | ----------- | ---------------------- |
| 提效 | 单页上线周期 | 3 人天      | ≤ 2 小时               |
| 提效 | 前端参与度   | 每页必介入  | 0 介入（仅复杂定制时） |
| 提效 | 需求响应速度 | 排期 2-3 天 | 当天上线               |

**隐性收益：**

- 把前端从重复劳动解放出来，去做真正有技术含量的工作
- 沉淀"活动页组件库"，组件越攒越多，后续页面越搭越快（复利效应）

## 3. 目标用户与使用场景

### 3.1 目标用户：电商运营人员

| 特征     | 说明                                                 |
| -------- | ---------------------------------------------------- |
| 技术水平 | 非研发，不会写代码，能理解"拖拽、勾选、填表"         |
| 核心诉求 | 快、不出错、能自己控制上线节奏                       |
| 使用场景 | 大促前批量搭活动页；临时营销快速上线；日常商品推荐页 |

### 3.2 典型使用流程（用户视角）

```
登录平台
  → 新建活动页 或 从模板创建
  → 从左侧组件库拖入组件（轮播/商品/优惠券/公告...）
  → 右侧配置组件属性（图片、文案、跳转链接、样式）
  → 实时预览手机效果
  → 保存 / 一键发布 → 生成 H5 链接
```

### P0（MVP，没有它产品不成立）

| 功能         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| 三栏编辑器   | 左：组件库 / 中：手机画布 / 右：属性配置                     |
| 组件拖拽搭建 | 从组件库拖入画布，画布内可排序、删除、复制                   |
| 属性配置     | 选中组件后，右侧面板可视化配置属性（图片、文案、样式、跳转） |
| 实时预览     | 编辑结果即时呈现在手机画布，所见即所得                       |
| 页面保存     | 保存页面配置，可再次编辑                                     |
| 发布         | 生成可访问的 H5 链接                                         |

### P1（支撑规模化使用）

| 功能         | 说明                                                |
| ------------ | --------------------------------------------------- |
| 模板中心     | 从历史页面 / 官方模板一键创建                       |
| 组件库管理   | 组件统一注册，可新增、可配置                        |
| 微信分享配置 | 分享标题、封面图（活动页强依赖微信传播）            |
| 组件生效时间 | 组件可设置生效/失效时间区间（如优惠券到期自动隐藏） |

| ----------- | ---------------------- |

| 多人协作    | 多人同时编辑同一页面   |
| 数据统计    | 页面访问量、组件点击率 |

## 5. 关键产品决策（为什么这么设计）

### 决策 1：为什么是"实时预览"，而不是"保存后刷新看效果"？

活动页搭建是**高频试错过程**。运营调一个颜色、换一张图，需要**立刻**看到效果才能判断好坏。若每次都要"保存→刷新"，体验会让人崩溃。所以"所见即所得"是**核心体验**，不是加分项。

### 决策 2：为什么是"组件化"，而不是"自由画布"？

自由画布（任意摆放）对非研发用户**太自由**，容易搭出乱版面。而电商活动页内容**有限且固定**——就是那十几种组件。组件化把"能做的事"约束在安全范围内，**降低门槛、保证质量**。

> 给非专业用户做工具的关键：**用约束换效率。**

### 决策 3：组件的"数据配置"与"最终渲染"为什么要分离定义？

一个"商品组件"：运营看到的是"选商品、调样式"的表单；用户看到的是最终渲染的商品卡片。两者共享同一份**数据契约（Schema）**——运营配出的数据 = 渲染端读的数据。这个分离让"新增一个组件"变成"定义 Schema + 写渲染"，而不是改一堆散落代码。

## 6. 非功能需求

| 维度     | 要求                                    | 理由                     |
| -------- | --------------------------------------- | ------------------------ |
| 性能     | 属性编辑反馈延迟 < 100ms                | 否则"实时预览"体验打折   |
| 兼容     | H5 需在微信 webview、手机浏览器正常运行 | 活动页主要通过微信传播   |
| 数据安全 | 编辑过程有草稿保护，防误关丢数据        | 运营搭半天页面丢了会崩溃 |
| 扩展性   | 新增组件无需改动编辑器核心              | 支撑组件库持续沉淀       |

---

## 7. 验收标准（达成目的的证明）

- ✅ 运营独立完成一张活动页搭建 + 发布，全程无需前端协助
- ✅ 单页搭建时间 ≤ 2 小时（含图片上传、配置、发布）
- ✅ 新组件接入周期 ≤ 1 天（从"提出"到"可在编辑器使用"）

---

## 8. 范围边界（明确不做什么）

| 不做                     | 理由                       |
| ------------------------ | -------------------------- |
| 自由布局画布（绝对定位） | 与"组件化约束"冲突，先不做 |
| 复杂动画/视频编辑器      | 活动页当前无此强需求       |
| 数据大屏 / 报表          | 与活动页搭建场景无关       |
